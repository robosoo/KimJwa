01응시 준비

시험 시작 전, 감독 환경부터 연결해

09:40은 미리 접속하라는 권고 시각이야. 10:00~14:00 전체 시험 시간은 별도이며 접속이 늦어져도 14:00 종료가 연장되지는 않아.

  1. PC에서 개인 응시 링크 열기규정을 끝까지 읽고 동의해. 최신 Chrome/Edge, PC 한 대와 모니터 한 대, 웹캠을 준비해.
  2. PC 웹캠과 전체 화면 공유 설정얼굴 전체와 양쪽 귀가 보이는지 확인해. 브라우저의 ‘탭’이나 ‘창’이 아닌 전체 화면을 선택해.
  3. 휴대폰 Cofa Proctor 연결설치 QR은 스마트폰 기본 카메라로, 시험 세션 연결 QR은 Proctor 앱 안에서 스캔해. PC에서 연결 완료 상태를 확인해.
  4. ‘과제 시작’ 누른 후 녹화·본인 확인휴대폰을 세로 거치하고 실물 신분증을 얼굴 옆에 들어 확인받아. 안경 착용 시 안경 앞면과 양쪽 다리를 확인하는 절차가 안내돼 있어.

1회 제공되는 사전 체험으로 README·터미널·Codex·Browser·메신저·감독 연결을 점검해. 체험 과제는 평가에 반영되지 않아.

02문제 파악

코딩보다 먼저 README와 요구사항

문제를 정확히 이해하지 못한 채 AI에게 “만들어 줘”부터 말하면, 작동해도 과제의 목적과 다를 수 있어.

  1. README.md와 관련 파일 읽기목적·필수 기능·제출 파일·제약조건을 따로 적어봐.
  2. 모호한 업무 조건은 ‘업무 담당자’에게 묻기이 프로그램을 누가 쓰는지, 가장 불편한 점은 무엇인지, 어떤 상태를 구분해야 하는지 질문해.
  3. 플랫폼 사용법은 ‘Cofa Helper’에게 묻기터미널·Browser·제출 버튼을 모르겠다면 업무 담당자가 아니라 Cofa Helper를 이용해.
  4. 요구사항과 검증 조건 구분하기필수 기능을 만들고 나서 무엇을 눌러 성공 여부를 판단할지 함께 정해.
연습용 Codex 첫 지시 예시

“README.md를 읽고 필수 기능, 제출물, 불명확한 조건을 구분해 줘. 모호한 업무 요구는 질문으로 정리해 줘. 아직 코드를 수정하지 마.”

공식 출처: 상세 가이드 pp.2–3(IDE, README, 메신저). 작업을 정리하는 순서는 학습용 권장 방법이며 공식 채점표가 아니야.

실제 Codex 실행이 아닌 순서 시뮬레이션이야. 설명을 보려는 버튼이 아니라 명령 진행을 연습하는 버튼만 있어.

승인 대기는 사용자가 허용·거절을 판단해야 하는 상태, 실행 중은 작업 진행 중, 완료는 AI 요청이 끝난 상태야. 완료만으로 프로그램 검증이나 시험 제출을 끝냈다는 뜻은 아니야.

서버 프로세스가 실행 중인 터미널을 종료하거나 Ctrl+C를 누르면 서버가 중단될 수 있어.

04직접 검증

프로그램이 보이는 것과 작동하는 건 달라

  1. 터미널에서 서버 실행 상태 확인실제 서버 로그에 표시된 PORT를 읽어.
  2. Browser에 PORT·URL 경로 입력3000은 가이드의 예시일 뿐 고정값이 아니야. 서버 바인딩은 0.0.0.0인지 확인해.
  3. 원형 새로고침 버튼으로 연결연결되지 않으면 서버 종료·PORT·바인딩·경로 순서로 좁혀가.
  4. 직접 눌러보고 입력하기목록·버튼·이동·예외 처리·수정 결과를 확인한 뒤 README 요구사항과 대조해.
Browser 연결 · 실패 원인 찾는 연습

가상 서버는 PORT 4173, 경로 /를 사용한다고 가정해. 실제 네트워크 연결은 없어.

어떤 설정이 실제 서버와 일치하는지 확인해 봐.

마지막으로 파일 저장

저장 중과 저장됨은 달라. Codex가 열려 있는 파일을 수정하면 ‘외부 변경 감지’가 표시될 수 있어. 외부 변경 불러오기는 디스크 내용을 가져오고, 현재 내용으로 저장은 에디터 수정 내용을 디스크에 반영해. 두 버전을 비교하고 선택해.

검증됐다는 근거

서버 실행 로그, 입력→버튼 클릭→실제 결과, 요구한 파일 경로·저장 상태, 실패한 조건을 수정한 후 재시험한 기록을 확인해.

공식 출처: 상세 가이드 pp.2–3, p.5. 검증 증거 정리 방법은 학습용 권장.

05제출 확정

미리보기와 최종 확정은 다르다

‘제출하고 문제풀기’는 제출 미리보기 화면에 들어가는 동작이고, 미리보기를 닫으면 파일을 수정할 수 있어. 반면 ‘제출물 확정하고 문제풀기’를 진행한 뒤에는 제출 파일을 수정할 수 없어.

  1. README 제출 파일·경로·저장됨 상태 확인미리보기에는 일부 파일만 표시될 수 있으므로 보이는 목록을 전체 제출물로 단정하지 마.
  2. 미리보기에서 마지막 확인수정할 점이 있으면 돌아가고, 확인이 끝났다면 최종 확정해.
  3. 질문 준비 대기제출물과 작업 기록을 바탕으로 질문이 만들어져. 일반 안내 약 5분, 상세 화면 예상 최대 10분 및 재시도 가능성이 있어.
제출 버튼의 되돌릴 수 없는 지점 · 조작 연습

가상 제출 화면만 바뀌며 실제 파일 제출·잠금·질문 생성은 없어.

작업 중 · 필수 파일과 저장 상태를 확인해.
기억할 함정

제출 미리보기 중에도 작업 시간은 계속 흐르고, 14:00 전체 종료 시점은 그대로야. 약 10분 전에 제출을 시작하라는 건 학습·시간 관리상 권장이지 의무 제출 마감 시각이 아니야.

오류가 반복되면 상단 문제 신고에 발생 시각·단계·직전 동작·오류 문구를 적어. 키·토큰·비밀번호는 포함하지 마. 신고만으로 타이머가 정지하거나 연장되지 않고, 본인 프로세스의 과도한 OOM은 구제 대상이 아니야.

2. 핵심 단서 — ‘업무 담당자’가 존재하는 이유

2026년 10월 16일 구한모 Cofa Probe PO와 조정석 엔지니어의 인터뷰에서는 기존 Cofa Probe 과제가 짧고 불완전한 업무 요청으로 출발하며, 가상의 현업 담당자에게 직접 물어 요구사항을 끌어내도록 설계됐다고 설명해. 일부러 모든 조건을 먼저 알려주지 않는 거야.

실제로 소개한 기존 과제는 PUBG 이스포츠 선수의 인터뷰 연습·코칭 서비스였어. 선수가 혼자 답변을 연습하고 기존 코칭 방식도 서비스에 담을 수 있게 해달라는 짧은 요청에서 출발하지. 참가자는 가상 인터뷰 담당자에게 현재 코칭 방식과 원하는 동작을 물어야 했어.

  1. 짧고 모호한 현업 요청 받기
  2. 가상 현업 담당자에게 질문해 필요 조건 발견
  3. AI에게 구현 지시하고 결과·예외조건 확인
  4. 결정 이유·실제 동작을 본인 언어로 설명
내 추론: 이번 SK하이닉스 공식 PDF에도 ‘업무 담당자’가 있으니, 단순 구현 속도와 별개로 무엇을 만들어야 할지 알아내는 능력을 관찰할 가능성이 커. 하지만 앞의 PUBG 예제는 기존 Cofa 사례이지 이번 2차 기출 문제가 아니야.

업무 담당자에게는 목표·사용자·입력·우선순위·예외조건을, Cofa Helper에게는 시험 플랫폼과 도구 조작법을 묻는 역할 구분도 중요해.

근거: 제작진 인터뷰, 이번 시험 응시환경 상세 가이드 p.2.

3. Cofa Probe가 공개한 평가 기준: 기술·의도·인지

[Cofa 공식] AI Native 역량은 특정 도구를 얼마나 외우는지가 아니라 제한된 자원 내에 AI의 장점·한계를 활용해 결과물을 책임지는 능력이라는 설명이 있어.

Technique — 기술 관리프로그램 실제 실행·완성도, 적절한 아키텍처, 유지·확장 가능한 구조, 보안 및 시크릿 관리.
Intent — 의도 관리목표·제약·완료 기준 정의, AI 작업 분해·위임, 지시 방향 수정, 실패 후 재검증.
Cognition — 인지 관리왜 그 구조인지, 어떻게 동작하고 어디서 깨지는지, 본인 산출물에 근거해 설명하는 능력.

제품 설명은 소스코드 외에도 대화·프롬프트·도구 설정·검증 실행 흔적이 수집되고, 사후 Q&A의 답이 제출 내용과 일치하는지를 평가한다고 소개해. 세 축의 세부 루브릭과 근거도 평가자에게 제공된다고 설명하지.

공개된 긍정적 신호

  • 완료 조건·수용 기준이 구체적인 AI 프롬프트
  • 실패 → 수정 → 같은 검증으로 재통과한 작업 기록
  • 선택 이유와 기각한 대안의 기록
  • 다른 세션도 이어받을 수 있는 목표·제약·판단 의도 문서(일반 Cofa 예시: CLAUDE.md)
  • 실제 제출한 코드·파일·기능과 모순되지 않는 답변

공개된 부정적 신호

  • “알아서 잘 만들어 줘”식의 통짜 위임
  • AI의 완료 보고를 직접 검증하지 않고 수용
  • 본인 프로그램과 무관한 일반론 답변
  • 없는 파일·API·기능이 존재한다고 설명
  • 실익 없는 도구·MCP 남발로 핵심 작업이 흐려짐
구분 필수: 이것은 Cofa Probe의 일반 공개 평가 프레임이지 SK하이닉스 2차의 정확한 가중치·세부 채점표가 공개됐다는 뜻이 아니야. 기존 행사에서 개인 Harness·Skill 반입이 허용되었더라도 이번 대회 개인 파일 업로드·별도 AI 연결 제한을 우선해.

연관 연구: 기술·인지·의도 부채

Margaret-Anne Storey의 2026년 논문 From Technical Debt to Cognitive and Intent Debt는 다음 위험을 구분해.

  • 기술 부채: 코드의 불량한 구조·선택 때문에 변경이 어려워짐.
  • 인지 부채: 시스템을 이해하고 결과를 예측할 수 있는 사람들의 이해가 약해짐.
  • 의도 부채: 목표·제약·선택 근거가 기록되지 않아 시스템이 무엇을 위해 있는지 흐려짐.

AI로 결과물이 빨리 나와도 왜 만들었고 어떻게 동작하는지 모르면 의도·인지 측면에서 취약할 수 있어. 이 해석은 제출 후 AI 없이 설명하는 시험 형식과 맞아떨어지지만, 논문이 이 시험의 채점표를 검증했다는 뜻은 아니야.

4. 출제 유형에 대한 내 상대적 예상

실제 주제·기술 스택은 미공개야. 아래는 공식 확률이나 기출 정보가 아닌 관련 단서에 기초한 정성적 순위야.

유형내 예상근거와 반증
작은 업무용 서비스·웹 도구 제작높게 봄업무 담당자·구현 환경·Browser·서버 사용 설명이 맞물림. 반면 Browser는 공통 사용 설명일 수 있음.
데이터 가공·검증·분석 결과물높게 봄외부 행사 정보의 ‘데이터 활용’ 표현과 파일·코드·문서 작업 환경. 비공식 설명이라 확정 불가.
업무 자동화·CLI 프로그램충분히 가능터미널·Codex·파일 편집·실행 검증 환경과 호환됨.
계획·분석 문서 중심가능하지만 상대적으로 낮게 봄문서 작성은 가능하지만 실행·검증 기능도 상세히 제공됨.
고급 반도체 회로설계 또는 대규모 AI 모델 학습상대적으로 낮게 봄2차는 AI Native 공통 역량 검증이며 전문 반도체 문제는 본선과 구분됨. 다만 완전히 배제할 수 없음.
중심 가설: 현업 데이터를 다루는 작은 프로그램 또는 업무 서비스. Python 데이터 처리 + 간단한 화면, 자동화 도구 + 결과 문서 등 여러 조합이 가능해. 웹서비스만 연습하거나 프롬프트 질문만 연습하는 건 모두 편향된 준비야.

5. 출제자 관점의 가상 과제와 변별력

예상형 모의과제 — 실제 기출·유출 문제 아님

“한 부서에서 매일 여러 파일로 접수되는 문제를 수작업으로 정리하고 있습니다. 담당자가 문제를 빠르게 파악하고 처리할 수 있도록 개선해 주세요.”

처음 요청에는 입력 파일 형식, 처리 상태 분류, 중복 판단 기준, 우선순위, 오류 데이터 취급, 결과 표시 방법이 빠져 있다고 가정해. 현업 담당자에게 직접 물어야 해결 방향이 명확해져.

참가자 A · 바로 구현Codex에게 대시보드 전체를 한 번에 만들어 달라고 해. 화면은 멋져도 실제 중복 기준과 업무 순서를 틀릴 수 있어.
참가자 B · 조건부터 발견현행 업무·병목·처리 기준을 묻고 필요한 기능만 구현. 정상 입력·빈 값·중복·오류를 테스트하며 수정·재검증해.

내 해석: Cofa가 공개한 철학과 부합하는 행동은 B야. 다만 실제 SK하이닉스 시험의 점수 차이가 이렇게 발생한다고 확정할 수는 없어.

제작진 인터뷰에서는 AI에게 “구현 전부 해 줘”라고 하면 초안은 빠르게 나오더라도 고치느라 3시간을 허비하고 토큰도 낭비할 수 있다고 경고해. 읽기만 하는 요구에 불필요한 쓰기 방어까지 추가하는 과설계도 부정적 예로 소개했어.

근거: 제작진 인터뷰 · 공식 제품 평가 설명. 이 가상 문제와 A/B 대조는 학습을 위한 창작.

6. 실제 연습에서 적용할 문제 해결 순서

프롬프트 기교를 암기하기보다 판단하고 검증하는 순서를 익히는 전략이야. 공식 강제 순서나 배점표는 아니야.

  1. README를 읽고 명시된 요구·아직 모르는 요구 구분: 필수 기능·제출 파일명·제약·예외조건을 정리하고 안내에 없는 필수조건을 임의로 만들지 않아.
  2. 가상 업무 담당자에게 질문: 사용자·현재 업무·입력 데이터·불편·우선순위·예외상황·성공 기준을 확인해. Cofa Helper의 플랫폼 안내와 역할 구별.
  3. 가장 작은 검증 가능한 결과물 정하기: 불필요한 화면·기술·도구를 제외하고 실제 필요한 기능부터 구현.
  4. Codex를 주도하며 구현: 목표·제약·완료 기준을 설명하고 작업을 쪼개 맡긴 뒤 명령·파일 변경·권한 위험을 검토.
  5. 실패 조건을 직접 검증: 정상 입력뿐 아니라 빈 값·중복·오류 데이터 테스트. 실패→수정→같은 조건 재검증 기록.
  6. 자신의 결정과 한계를 이해한 채 제출: 선택 이유·기각한 대안·미구현·미검증 항목을 실제 결과물에 맞춰 정리하고 AI 없이 설명 가능해야 해.
주의: Skill·MCP·Harness를 많이 설치하는 자체가 목표가 아니야. Cofa의 다른 행사에서 허용된 개인 Harness 반입은 이번 시험 규정과 다를 수 있어. 이번 시험에서는 개인 파일 업로드, 허용되지 않은 외부 AI, Git Push·외부 전송, Computer Use 제한을 지켜야 해.
